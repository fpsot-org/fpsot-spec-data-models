= FPSOT data models specification
include::_fpsot-terms.adoc[]

This specification sets how {abbr-fpsot-first} projects define and publish the data models of their entities.
A data model names the entities that systems exchange and keep.
It also gives the fields of each entity, with their types and references.
Each model has one link:https://linkml.io/linkml/generators/index.html[LinkML] source, and tools generate its other forms.
The first subject area is Party: the people and organizations that a public body deals with.

Every part of a model is optional.
An institution can use its own party records, Apache OFBiz or another system.
That system can run inside its program or as a remote service.
The institution conforms when the data it exchanges takes the form of the model.

The rules come in eight parts.

* xref:principles.adoc[Principles] say what a model describes and what it leaves to each system.
* xref:linkml.adoc[LinkML source and generated files] sets the source of a model and the checks on the files generated from it.
* xref:names-types.adoc[Names, keys and types] applies the naming and data types specifications, and maps the dates of Apache OFBiz to intervals.
* xref:codes-contact.adoc[Codes, names and contact data] binds codes to vocabularies, and sets the form of contact data.
* xref:party.adoc[Party subject area] sets the entities of the first subject area.
* xref:history-extensions.adoc[Audit, history and extensions] sets the audit instants, how a model keeps history and where a jurisdiction adds fields.
* xref:versions.adoc[Versions and deprecation] sets how a model changes without breaking stored data.
* xref:persistence.adoc[Persistence and tooling] covers storage mappings and the planned tools.

== Related specifications

This specification builds on other {abbr-fpsot} specifications.
The naming specification sets the names of classes, fields and codes, and when they may change.
The data types specification sets the form of each value, such as identifiers, instants and intervals.
The vocabularies specification sets how a field binds to a controlled vocabulary.
The internationalization specification sets the rules for names of persons, postal addresses and language tags.

The writing, documentation and diagrams specifications set how to write and draw the model's documentation.
How an {abbr-api-first} serves the entities of a model belongs to the {abbr-fpsot} specifications on {abbr-api} design.

== LinkML model

The file `model/party.yaml` defines the Party subject area in link:https://linkml.io/linkml/generators/index.html[LinkML].
The folder `model/generated/` holds the files generated from it.
The folder `model/examples/` holds valid and invalid data and an example profile for Québec.
The script `model/test-model.sh` checks them all.

== Conformance

[quote, 'link:https://www.rfc-editor.org/info/rfc8174[RFC 8174]']
____
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 (link:https://www.rfc-editor.org/info/rfc2119[RFC 2119], link:https://www.rfc-editor.org/info/rfc8174[RFC 8174]) when, and only when, they appear in all capitals, as shown here.
____

The keywords follow requirement WRT-010 of the {abbr-fpsot} writing specification.
The French version uses the French keywords of WRT-011.

A data model conforms when its source, its generated files and its checks meet every MUST rule for a model.
A system conforms when the data it exchanges for each part that it implements meets the model, under DMO-004.
A jurisdiction profile conforms when it meets DMO-053 to DMO-056.
