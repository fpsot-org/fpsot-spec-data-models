= Names, keys and types
include::_fpsot-terms.adoc[]

These rules apply the {abbr-fpsot-first} naming and data types specifications to the elements of a model.
They also map the date pattern of Apache OFBiz to the intervals of the data types specification.

== Names

[[DMO-020]]
*DMO-020.* A class name MUST be a singular noun in UpperCamelCase, such as `PartyRole`.
Slot names and enumeration values MUST follow the naming specification, such as NAM-010, NAM-040 to NAM-043 and NAM-060.
Every name MUST use the term of the writing term base when one exists, under NAM-002.
A name MUST NOT shorten a word, under NAM-005.
So the model writes `Organization` and `ContactMechanism`, where Apache OFBiz writes `PartyGroup` and `ContactMech`.
UpperCamelCase is the usual form for LinkML classes, and it matches the class names of generated code.

== Keys and references

[[DMO-021]]
*DMO-021.* Each entity MUST have a slot named `id`, marked `identifier: true`, with the type `Uuid` of the data types specification.
A new identifier SHOULD be a version 7 {abbr-uuid-first}, under DAT-063, or a version 4 one under DAT-064.
An identifier that another body issues, such as a business number, MUST NOT be the `id`.
A key that a system creates never changes and reveals nothing, under DAT-062.
Another body can change its number, give it to someone else later, or issue none at all.

[[DMO-022]]
*DMO-022.* A reference to another entity MUST be a slot that holds its `id`, such as `partyId`.
A model MUST NOT use a key made of several fields.
An entity that links two others, such as a party role, MUST still have its own `id`.
Apache OFBiz keys such a link by the two references and a start date.
With its own `id`, a link can change its period and keep its key.
Other data can also refer to it.

== Periods of validity

[[DMO-023]]
*DMO-023.* An entity that holds for a period MUST have a slot named `validity`, which is an interval under DAT-023.
The model MUST NOT use two separate fields for the start and the end.
The range SHOULD be `DateInterval` for a fact that changes on a calendar day.
It SHOULD be `InstantInterval` for a fact that changes at a moment.
One form lets every tool test whether a record is valid on a given day.

The table maps the date pair of Apache OFBiz to an interval.

[cols="2,3",options="header"]
|===
|Apache OFBiz |{abbr-fpsot} model
|`fromDate` |`validity.start`
|`thruDate` |`validity.end`
|Empty `thruDate` |No `end` member
|Date and time on the server clock |`Instant` in {abbr-utc-first}, or `CalendarDate` when only the day matters
|`fromDate` in the primary key |Not in any key, since the entity has its own `id`
|===

The link:https://github.com/apache/ofbiz-framework/blob/e103805ef7f15e9f3802e97b0a5c8a6cb47032b2/framework/entity/src/main/java/org/apache/ofbiz/entity/util/EntityUtil.java[OFBiz date filter] treats a record as valid when the moment is on or after `fromDate` and before `thruDate`.
That is the same rule as DAT-023: the interval holds its start but not its end.
A mapping therefore copies the two values with no shift of one day or one second.

== Types

[[DMO-024]]
*DMO-024.* Each slot MUST use the type of the data types specification that matches its value.
Examples are `Instant` for a moment, `CalendarDate` for a date and `Money` for an amount.
Text that {abbr-fpsot} or an institution publishes in several languages MUST use `MultilingualText`.
Text that a person enters MUST be a plain string, kept as the person wrote it.
Examples are a name or an address.
A name or an address has one form in its own language, under LOC-055, and nobody translates it.
